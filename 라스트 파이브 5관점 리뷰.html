「라스트 파이브」 5관점 리뷰

5인 온라인 능력자 배틀로얄 FPS 웹 프로토타입을 실제 플레이어, 디자이너, 시장 분석가, 보안 엔지니어, 총괄 책임자 다섯 관점으로 살펴본 결과입니다. 각 관점은 실제로 플레이하고 인터넷 자료를 조사했습니다.

대상: 웹 프로토타입 + 기획 문서 파일 수정 없음 코드 확인 표시 = 코드에서 직접 확인한 항목
한눈에 지금 고칠 것 공통 지적 실사용자 디자인 시장 보안 총괄 로드맵
한눈에

잘 만든 뼈대, 남은 문제 세 가지

로비 → 파밍 → 교전 → 결과까지 한 판이 처음부터 끝까지 돌아가고, 2~5인 온라인과 빈자리 봇도 됩니다. 기획 문서끼리 서로 잘 연결돼 있습니다. 다만 아래 세 가지는 다음 단계로 가기 전에 정리해야 합니다.

보안

링크를 공개하면 안 되는 상태

누구나 콘솔 한 줄로 다른 사람을 죽음 처리하거나 강퇴할 수 있고, 로비에 스크립트를 심을 수 있습니다. 지금은 아는 사람끼리만 쓰세요.

재미

숨어 있으면 이기는 판

봇끼리 싸우고 자기장에서 죽어서, 아무것도 안 해도 처치 0으로 1위가 나옵니다. 플레이어는 "최후의 1인!"이 허무하다고 느낍니다.

시장

실패가 이어진 콘셉트

능력 배틀로얄 게임들(Spellbreak, Super People, SUPERVIVE)은 출시 후 동접이 처음의 1~5%까지 떨어졌습니다. 내세우는 방식을 바꿔야 합니다.

우선순위

지금 바로 고칠 수 있는 것

작고 효과가 확실한 순서입니다. 1~4번은 코드만 고치면 되고, 5번은 기획 결정이 필요합니다.

  1. 로비 XSS 막기와 받는 값 검사보안 · 높음코드 확인

    로비 목록의 인원 수 r.count가 그대로 화면에 들어가서, 누군가 여기에 스크립트를 넣으면 로비를 보는 모든 사람의 브라우저에서 실행됩니다. 숫자·글자 형식을 확인하고 길이를 제한합니다.

    js/lobby.js:24
  2. 내가 죽었을 때 처치한 쪽의 처치 수 올리기버그 · 중간코드 확인

    내가 죽을 때 실행되는 die()가 처치한 쪽의 처치 수를 올리지 않습니다. 그래서 나를 처치한 쪽의 처치 수가 결과 화면에 빠집니다.

    js/hud.js:1410 (die) · 1373 (kill)
  3. 혼자 연습 안내 문구와 닉네임 자동 생성사용성 · 중간코드 확인

    혼자 연습에서도 Esc 메뉴에 "온라인 게임이라 메뉴를 열어도 게임은 계속됩니다"가 나옵니다. 또 닉네임이 없으면 혼자 연습 버튼이 안내 없이 막힙니다. 닉네임이 없으면 자동으로 만들어 주세요.

    index.html:231 · js/lobby.js
  4. 외부 스크립트 무결성 검사와 보안 헤더보안 · 중간코드 확인

    three.js·supabase-js를 불러올 때 파일이 바뀌었는지 확인하는 integrity 속성이 없습니다. vercel.json에 CSP 같은 보안 헤더도 추가합니다.

    index.html:292-293 · vercel.json
  5. 능력 피해 상한 30을 지킬지 정하기기획 결정코드 확인

    문서는 "능력 직접 피해는 한 번에 최대 30"이라고 하는데, 실제로는 돌진 40, 지면 강타 50, 연쇄 번개 35, 유성 90입니다. 원칙을 지키려면 수치를 내리고, 버린다면 문서를 고칩니다.

    ABILITY.md:17 · js/data.js
겹치는 지적

여러 관점이 함께 짚은 것

주제지적한 관점핵심
봇 의존사용자 · 시장 · 총괄빈자리 봇은 꼭 필요하지만, 봇인 걸 숨기면 반발이 큽니다(Super People, Fortnite 사례). 봇이라고 표시하고, 사람 1명 + 봇 4명 판도 재미있어야 합니다.
좁은 화면 HUD 겹침사용자 · 디자인 · 총괄화면 폭이 900px보다 좁으면 키 안내, 능력 바, 무기 슬롯, 손에 든 총 모델이 서로 겹칩니다.
첫 경험(온보딩)사용자 · 디자인닉네임이 없으면 막히는데 안내가 없고, 시작하자마자 키 20개짜리 조작표가 한꺼번에 뜹니다.
범위와 순서시장 · 총괄Godot 서버 네트워크가 가장 큰 일정 위험입니다. 웹 버전은 재미를 확인하는 데만 쓰고 기능 추가를 멈추자는 의견입니다. 능력과 무기 수도 줄이자고 합니다.
관점별 상세

다섯 관점의 피드백

실사용자

첫 능력을 얻는 순간이 가장 재미있었지만, 내가 아무것도 안 해도 판이 끝납니다.

직접 해 보니

  • 몇 초 만에 무기·탄약·조끼를 주워서 "30초 안에 첫 무기" 목표를 넉넉히 지킵니다.
  • 티켓을 써서 분신술을 얻고 바로 써 보는 흐름이 좋았습니다. 큰 지도와 결과 화면도 깔끔합니다.
  • 봇끼리 싸우다 자기장에서 죽어서, 교전 한 번 없이 1위가 나왔습니다.
  • 집 출입구 벽 모서리에 걸려 1.5초 동안 약 1m밖에 못 갔습니다.
  • 감도를 숫자로 넣을 수 없고, 지도에서 "내 스폰"과 지명이 겹칩니다.

제안

  • 높음첫 대기 시간을 120초에서 60~90초로 줄이고, 봇이 사람 쪽으로 오게 합니다.
  • 높음대기실·킬피드·결과에 봇 표시를 붙입니다.
  • 높음처음에는 이동·사격·줍기·티켓·능력 키만 보여 주고, 나머지는 필요할 때 하나씩 알려 줍니다.
  • 중간티켓을 쓰면 능력 2~3개 중 하나를 고르게 해서 운이 나쁜 판을 줄입니다.
  • 중간일찍 죽은 사람은 바로 다음 판을 기다리거나 연습장으로 갈 수 있게 합니다.
  • 낮음혼자 연습에서는 Esc를 누르면 일시정지합니다.

참고: 이 에이전트는 "가한 데미지 0"을 버그로 의심했지만, 코드에서는 피해가 집계되고 있습니다(js/hud.js:764). 쏜 총알이 빗나갔을 가능성이 큽니다.

디자인

밝은 지면 위에서 HUD 글자가 거의 보이지 않습니다. 가장 먼저 대비를 고쳐야 합니다.

관찰

  • 능력 이름 글자 대비는 1.2:1, 회색 보조 글자는 2.2:1입니다. 접근성 기준은 4.5:1입니다.
  • 10~11px 글자가 많습니다. Xbox 접근성 가이드는 1080p에서 최소 18px을 권합니다.
  • 조명이 강하고 톤매핑이 없어서 지면이 형광 연두로 보이고 명암 차이가 거의 없습니다.
  • 체력바 숫자가 잘 안 읽히고, 헬멧·조끼는 "헬멧 –" 같은 글자로만 표시됩니다.
  • 꾸미기 패널 내용이 넘치고, 지도 라벨이 잘리고, 접근성 설정이 없습니다.
  • 기본 색 토큰은 잘 정리돼 있지만, hud.css에는 토큰을 쓰지 않은 색이 많습니다.

제안

  • 높음HUD 배경판 불투명도를 0.72 이상으로 올리고, 글자에 외곽선을 넣습니다. css/hud.css
  • 높음좁은 화면에서는 키 안내를 10초 뒤 숨기고, 손에 든 총 모델 크기를 줄입니다.
  • 높음주변광을 0.15 안팎으로 낮추고 sRGB 출력과 ACES 톤매핑을 켭니다. 캐릭터는 환경과 밝기를 다르게 합니다. js/world3d.js:354
  • 중간체력바에 피해 흔적을 남기고, 방어구는 레벨 아이콘으로, 탄약 부족은 아이콘으로 함께 표시합니다.
  • 중간설정에 HUD 크기, 배경판 불투명도, 조준점 색, 색약 모드를 추가합니다.
  • 낮음hud.css의 하드코딩 색을 토큰으로 묶습니다.

시장

"배틀로얄"보다 "친구 5명이 하는 파티 슈터"로 내세우는 편이 살아남을 가능성이 큽니다.

현황

  • 2025년 배틀로얄 플레이 시간은 전년보다 27% 줄었고, 그 안에서 Fortnite 비중은 77%입니다(Newzoo).
  • 2025년 Steam 출시작은 약 2만 개이고, 그중 65.9%는 매출 1,000달러 미만으로 추정됩니다.
  • 한국 PC방은 LoL이 36%를 차지하고, 2025년 총 이용 시간은 약 6% 줄었습니다.
  • 지금 PRD에는 "과금 없음"만 있고 수익 모델은 정해지지 않았습니다.

제안

  • 최우선PUBG가 아니라 ROUNDS 같은 파티 게임과 비교되게 하고, 초대 코드·친구 초대를 대표 기능으로 둡니다.
  • 최우선사람이 없어도 사람 1명 + 봇 4명 판이 재미있도록 봇을 핵심 기능으로 다룹니다.
  • 높음CrazyGames·Poki 같은 웹 게임 사이트에 먼저 올려 다시 하는 비율을 잽니다.
  • 높음Steam은 저가 유료(5천~1만 원)로 하고, 무료 체험판이나 친구 패스를 둡니다.
  • 중간처음에는 방장 PC를 서버로 쓰는 방식으로 서버 비용을 0원에 맞춥니다.

프로토타입에서 지금

  • 받는 모든 값(로비, presence, 패킷)의 형식을 검사합니다.
  • 강퇴·시작은 방장에게서, 아이템 허락은 판정자에게서 온 것만 받습니다. 피해와 넉백에는 상한을 둡니다.
  • SRI와 보안 헤더를 추가합니다.
  • Supabase 익명 로그인, private channel, RLS를 쓰고 "Allow public access"를 끕니다.

Godot 본편 설계에서

  • 서버가 모든 판정을 합니다. 클라이언트는 입력만 보내고, 명중은 서버가 시간을 되감아 확인합니다.
  • RPC는 보낸 사람과 값의 범위를 항상 확인합니다.
  • 보이는 적의 위치만 보내 월핵을 막습니다(Riot 방식).

실제 Supabase 프로젝트나 배포 사이트에는 아무것도 보내지 않았습니다. 코드와 공식 문서만 보고 판단했습니다.

이틀 만에 한 판 전체를 만든 속도는 좋습니다. 이제 웹 기능 추가를 멈추고 가장 큰 위험인 Godot 네트워크를 먼저 확인할 때입니다.

진단

  • 문서와 data.js가 잘 맞고, 콘솔 오류가 없고, 프레임도 안정적입니다(중앙값 12ms).
  • 문서끼리 충돌합니다. 능력 피해 상한, SG-12 재장전 시간, 맵 티켓 수, 없는 UI_DESIGN.md 참조가 있습니다.
  • hud.js 1870줄 한 파일에 규칙, AI, 네트워크, HUD가 섞여 있습니다. Godot로 옮길 때 다시 쓰는 것은 수치와 규칙 설명뿐입니다.
  • PRD에는 "M1에서 네트워크부터 검증"이라고 했는데, 실제 작업은 웹 다듬기(봇 AI 등)에 몰려 있습니다.
  • 출시 경로, 예산, 플레이테스트 일정, 개발 인원이 아직 정해지지 않았습니다.

가장 큰 위험 3개

  • 1사람 수: 5명이 모이지 않으면 판이 안 잡힙니다. 봇은 꼭 필요하지만 봇에 너무 기대면 리뷰가 나빠집니다.
  • 2Godot 서버 네트워크: 래그 보상, 예측·보정, 되감기·분신처럼 서버 상태를 쓰는 능력 때문에 일정이 크게 늘어날 수 있습니다. 공개된 Godot 4 상용 FPS 사례도 거의 없습니다.
  • 3범위: 약 580시간 안에 무기 13종, 능력 19종, 로비 서버, DB를 넣는 계획입니다. 1인 FPS 사례(3,850시간)에 비해 매우 낙관적입니다.
